# 语音断句与完整播报调整（2026-09-30）

## 当前问题与实施边界

当前对话录音仍以能量和静音时长判断句尾；Sherpa 负责唤醒词，不能替代对话断句。短暂停顿可能被当作一句结束。截图中的 running 只能说明检测器状态，不能证明收到有效语音。

本轮已修复播报生命周期，尚未替换录音 VAD。服务端现有 TTS 会保留前 600 个字符；客户端现在将完整文本切为最多 300 个 Unicode 字符一段，优先在句末切分，按序合成和播放，不丢弃尾部。段间仍可能有网络合成等待。

## 已实现：先保证说完

- 默认关闭仅凭音量的自动打断，包括已保存的旧打断配置，避免扬声器回声误触发；保留用户主动停止。
- 网络播放以播放器完成事件为准，移除按音频大小估算完成时间的逻辑。每段三分钟保护超时属于失败，不再当作成功。
- 整条回复的所有分段播完后才恢复原来的监听模式，段间不提前打开收音。
- 停止使正在合成的旧请求失效；迟到音频不能重新播放。串行执行播放器操作，避免旧任务停止新任务。
- 系统 TTS 同样等待完成回调；播放错误向上层提示中心报告。

## 下一阶段：重新划分听与说的边界（待实施）

1. 建立单一麦克风所有者，明确唤醒、收音、等待回复、播报、恢复收音阶段。不同入口复用同一套断句策略与取消标识。
2. 对话收音引入逐帧语音活动判断；音量仅作为辅助诊断。保留约 300 毫秒的开头缓冲，避免吞首字；语音开始需连续确认，过滤短噪声。
3. 句尾先进入“等待续说”，短暂停顿后继续说时并回同一句。初始试验参数为约 900 毫秒静音确认，按实机语料调整；短语和弱声不直接丢弃。设置最长录音边界，达到边界时明确结束原因。
4. 唤醒与同一口气说出的指令保留衔接音频，避免切换录音器丢失“萌萌，帮我……”后半句。
5. 自动语音打断须在回声处理与真人语音判定验证后再启用。未满足条件时继续使用主动停止，不恢复能量触发方案。
6. 诊断记录首个语音时间、静音时长、结束原因、取消代次与播放完成原因；提示仍在右上角入口，不在主屏铺文字。
